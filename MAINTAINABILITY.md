# Maintainability & Readability Report

This report was generated from a full sweep of `src/` (UI layer + services/hooks/models/config) to identify what's hurting maintainability and readability. It's meant to be worked through over multiple sessions — check items off as they're addressed, and feel free to append new findings here as they come up.

## 🐛 Actual bugs (not just style)

- [x] **`clearSession` doesn't clear the session.** `AppReducer.ts`'s `CLEAR_SESSION` case called `localStorage.clear()` only, but `_themeMode` was read/written via `localStorage` while `_user` was read from `sessionStorage` at init but written to `localStorage` on every `SET_USER` — an inconsistent mix, so `sessionStorage` was never actually cleared. The reducer also returned a shape (`popularMovies`, `popularTVShows`) that didn't match `AppContextState` at all. **Fixed**: storage is now split by intent — `_themeMode` (a UI preference) consistently uses `localStorage`, `_user` (destined to hold auth state once login is implemented) consistently uses `sessionStorage` so it doesn't outlive the tab, and `CLEAR_SESSION` clears both stores and returns a properly-shaped state. _(Superseded for `_user`: once Firebase Auth landed, the user is no longer persisted by the app at all — Firebase keeps the session and an `onAuthStateChanged` listener rebuilds `user` on load. See "Auth state" below. `CLEAR_SESSION` itself was later removed — see "Auth & watch-list follow-ups".)_
- [x] **Hardcoded default search term.** `Navbar.tsx` — `useState('star wars')` as the initial search value. **Resolved indirectly**: search was removed from `Navbar.tsx` entirely (relocated to dedicated per-page search on the upcoming Movies/TV Shows pages — see the "Search relocation" note below), taking the hardcoded default with it. The extracted `SearchBar.component.tsx` takes `value`/`onChange` as controlled props with no built-in default — just don't reintroduce one when wiring it up on the new pages.
- [x] **`SummaryModal` bypasses the app's own data-fetching pattern.** `SummaryModal` hand-rolled `useState`/`useEffect` and called `movieService`/`tvService` directly — no caching, no retry. **Fixed**: it now fetches through `useQuery` (cached, retried). ~~Remaining nit: the query is inline in the component~~ — resolved: it uses the shared `useMediaDetails` hook (`src/core/hooks/`), the same cache as the watch list and Insights.

## 🔓 Type safety holes

- [x] `User` is `export interface User {}` — an empty interface, equivalent to `any`; `AppContextState.user` has no real type checking. **Fixed**: `user.model.ts` defines the fields the app reads (uid, email, displayName, photoURL, phoneNumber, emailVerified, providerIds, created/last-sign-in times) plus `toUser()` to build it from a Firebase user; `AppContextState.user` is `User | undefined`.
- [x] `AppReducer(state: any, action: any)` — no discriminated union for actions despite `AppContextType` being well-typed. **Fixed**: `AppAction` (in `types.ts`) is a discriminated union of the five actions, each with its own payload type, and the reducer is `(state: AppContextState, action: AppAction): AppContextState` (state only — the setters are added by the provider), with a `never` exhaustiveness check so an action added without a case fails to compile. Typing it exposed a real hole: the dialog/snackbar cases fell back to `payload || {}`, so `setSnackBarProps()` (closing the snackbar, `App.tsx`) stored `{}`, missing `open`/`message`; they now reset to `new SnackBarProps()` / `new AlertDialogProps()`.
- [x] `MovieListResponse`/`TvListResponse` type `results` as `(TvShow & Movie)[]` — an intersection that's structurally impossible for a real response to satisfy (a movie result can't have `TvShow`'s required `name`). Should be a `media_type`-discriminated union instead — the field already exists on both base types but is never used to discriminate. **Now actively surfacing**: `Home.page.tsx` (still typed with the wide `MediaItem = TvShow & Movie` for its genuinely-mixed hero carousel) has 3 pre-existing `tsc` errors from assigning the honestly single-type `useMovies`/`useTvShows` results into it — harmless today only because the real build never reaches these files (see the `tsconfig.json` item below), but a real fix, not just a lint nit. **Fixed**: `Media`/`MediaDetails` (`common.model.ts`) now declare `media_type: 'movie' | 'tv'` and each subtype narrows it; list responses are `TmdbListResponse<Movie>` / `TmdbListResponse<TvShow>`; `TmdbListService` stamps `media_type` onto every result; `Home.page.tsx`'s `MediaItem` is the union `Movie | TvShow`, narrowed with `isMovie`/`isTvShow`. The three `Home.page.tsx` errors are gone.
- [x] `ApiError`, `ApiOptions`, and most of `ApiService`'s methods lean on `any` for error/param shapes; `AlertDialogProps`/`SnackBarProps` even declare `state?: AlertDialogProps | any` (the `| any` makes the left side meaningless). **Fixed**: `ApiError.data`/`original`, request bodies and the generic defaults (`apiGet<T = unknown>` …) are `unknown`; errors are narrowed with `axios.isAxiosError`/`axios.isCancel` instead of `err?.response`; the 401-retry config is a typed `RetriableConfig`; query params use a shared `QueryParams` type (also in `tmdbList.service.ts`). The props constructors take `Partial<…>`, and dialog `title`/`content` are `ReactNode`. Typing honestly exposed two holes: `AlertDialogProps.onConfirm` was declared required but a reset dialog has none (now optional, called as `onConfirm?.()` in `App.tsx`), and `SnackBarProps.message` could end up `undefined` (now defaults to `''`). Verified against TMDB: success, a 404 (`ApiError` with status + body) and a 401. Still `any`, outside this item: `AppContextProvider`'s `children` and `TVShowDetails.episode_run_time`.
- [x] `TeamMemberCard.tsx` has zero prop typing at all — the only component missing a `Props` interface. **Moot**: the file was deleted as dead code.
- [ ] **Two `any`s left.** `AppContextProvider`'s props (`({ children }: any)` → `{ children: ReactNode }`) and `TVShowDetails.episode_run_time: any[]` (→ `number[]`). One-liners each.

The sign-in tab's "Back to sign in" arrow now flips like `CollectionSpotlight`'s. Verified: typecheck, tests, the dev server loads the new modules, and the plugin chain flips physical properties while leaving logical ones, `scaleX` and `/* @noflip */` alone. Not yet checked screen by screen in Arabic in a browser.

## 🔐 Auth & watch-list follow-ups

- [ ] **Terms/Privacy links bypass the router.** `UserAuthSignUpTab` uses `<Link href='/terms'>` / `'/privacy'` — plain hrefs ignore the `/StreamLens/` basename (they'd leave the app on GitHub Pages), and neither route exists. Add the routes and use `component={RouterLink} to=...`. **Half-done**: the hrefs are gone (they rendered as plain spans, so nothing navigates or leaves the app), but /terms and /privacy still don't exist — write the pages, route them, and switch these to `component={RouterLink} to=...`.
- [ ] **Terms sentence is concatenated from fragments** (`agreeToTermsPrefix` + link + `and` + link + "."), which fixes English word order into fr/ar. Use i18next `<Trans>` with one key containing both links.
- [x] **"Continue as guest"** in `UserAuthModal` has no `onClick` (it should at least close the modal).
- [x] **`CLEAR_SESSION` has no callers and doesn't sign out of Firebase.** Sign-out currently happens via `signOut(auth)` in the profile modal, with the listener clearing `user`. Either remove `clearSession` or make it the one sign-out path (`signOut` + storage + query cache). **Removed** (action, reducer case, context function and type). A dedicated sign-out path would only cover the button that calls it, while revoked/expired sessions, account deletion and sign-out in another tab bypass app code entirely — all of them reach `onAuthStateChanged(null)`, so that's where cleanup now lives. Its behavior was also wrong for the app: `localStorage.clear()` wiped the theme preference (and would wipe Firebase's own storage if it had fallen back from IndexedDB), and resetting `snackBarProps` would cancel a "signed out" message.
- [x] **Query cache isn't cleared on sign-out.** Watch-list keys are scoped by uid, so nothing leaks between accounts, but the previous user's data stays in memory. **Fixed**: the auth listener in `AppContextProvider` calls `queryClient.removeQueries({ queryKey: [WATCH_LIST_QUERY_ROOT] })` when the user becomes `null`. TMDB caches are kept (not per-user). New user-scoped queries should export a key root the same way and be added there.
- [x] **Watch list has no consumers or mutations yet.** When writes land: `useMutation` + `invalidateQueries({ queryKey: [WATCH_LIST_QUERY_ROOT, uid] })` (root exported from `watchList.service.ts`; sign-out already drops those queries). Storage is one document per user (`watchLists/{uid}`, the `WatchList` model stored as-is), so each write rewrites the whole `watch_list` array and must go through `runTransaction` to avoid losing a concurrent edit from another tab. **Done**: `setMovieWatched`, `setEpisodeWatched`, `removeEntry` and `addToWatchList` are all `runTransaction` read-modify-writes that skip the write when nothing changed; `useWatchListMutations.ts` wraps each one; and the Summary modal's "Save to watch list" button plus the episode checkboxes now read and write real progress (signed-out clicks open the now-global auth modal). "Mark all episodes as watched" now works too: `setEpisodesWatched` (one transaction for the season's aired episodes, toggling to unwatch once all are watched). Remaining: no optimistic updates, and sign-in doesn't resume the interrupted action. (It now runs against the real Firestore document daily.)
- [x] **Firestore security rules weren't in the repo** — the database was governed only by whatever the console had (test mode opens it to everyone until it expires, then denies everything). **Added** `firestore.rules` (owner-only `watchLists/{uid}`, everything else denied) plus `firebase.json`; deploy with `npx firebase deploy --only firestore:rules`. Not yet verified against the emulator.
- [x] **Unverified accounts silently lose the watch list.** `firestore.rules` now requires `email_verified`, so an email/password user who hasn't clicked the verification link gets `permission-denied` on every watch-list read and write — the UI just shows the generic error snackbar. Surface a "verify your email" state instead (the profile modal already has a resend action), or relax the rule. **Fixed**: `useWatchListGate` turns the blocked states into prompts (auth modal when signed out, a verify-email AlertDialog with a resend action when unverified), the list query no longer fires for unverified users, and a focus/visibilitychange listener in `AppContextProvider` reloads the Firebase user so verifying in another tab unblocks the app without a manual reload.
- [ ] **Watch-list entries aren't validated server-side.** Firestore rules can't iterate arrays, so the rules check only the document shape (`{ uid, watch_list }`, list, size <= 2000). A client could still write malformed entries into its own list. Per-entry validation would need the subcollection layout (one doc per title) or a Cloud Function.
- [ ] **Tests cover pure logic only.** ~~No tests exist~~ — outdated: Vitest runs 4 files / 50 tests (`insights`, `watchListMeta`, `collections`, `rhythm` utils). Still untested: `ApiService` (retry/backoff, error wrapping — testable by stubbing axios), and every component (needs `environment: 'jsdom'` and a jest-dom setup file — see CLAUDE.md).
